## 11. Context duplicate-evidence finding

Investigation constrained to existing preserved context `synonym--ee6b5af5c217` found:

- `relevant_internal_relationships`: 33 rows, including 24 `test_reference` rows
- `relevant_tests`: 20 rows
- exact duplicate deterministic rows within `relevant_tests`: none
- browser-visible duplicate-looking rows within `relevant_tests`: present
	- visible row key used by current template (`test_file`, `test_name`, `target_file`, `target_symbol`) collapses 20 deterministic rows to 8 visible keys
	- `test_ordering_independent -> vocab_utils.py::normalize_synonym_candidates` appears 6 times in browser-visible form
	- several other test names appear twice in browser-visible form

Conclusion:

- there are two distinct readability effects:
	- cross-section repetition by design (test-reference relationships shown in both Direct Relationships and Related Tests)
	- within Related Tests, multiple deterministic records render as identical-looking rows because key distinguishing fields are currently hidden
- distinguishing hidden fields include `source_line` and `test_info.reference_kind` (for example separate `import` and `call` references for the same test method and target symbol), and in general may also include class/kind metadata.
- duplication layer is therefore primarily browser/view rendering, not deterministic evidence corruption.

Safest 009.3 presentation rule:

- preserve all deterministic records;
- aggregate browser presentation by visible test-target key;
- show per-group evidence details (for example reference kinds and source lines) in expandable secondary detail;
- deduplicate only rows that are genuinely identical across the full deterministic identity fields.

This preserves audit fidelity while removing misleading apparent duplicates in primary view.
