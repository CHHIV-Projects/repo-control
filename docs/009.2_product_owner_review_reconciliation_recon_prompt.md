# Controlling Product Owner Findings

Treat the following as the controlling design findings from the completed M009.1 Product Owner review.

## A. General UI

- use more desktop width intelligently;
- reduce unnecessary left/right empty space;
- preserve readable prose widths;
- human-readable labels should lead;
- immutable machine IDs should remain available as secondary audit detail;
- normal operation should eventually avoid requiring visible CLI/server/tunnel management.

## B. Repository Selection

Current browser startup binds one repository.

Desired direction:

    controlled repository chooser

Requirements:

- choose only registered/approved repositories;
- no arbitrary browser filesystem path entry;
- switching repository changes Dashboard, Context, Snapshots, Comparisons, AI Review, and Workflow consistently.

## C. Dashboard — Git State

Current:

    Branch
    HEAD
    Workflow
    Git operation

Desired:

- human-readable commit information;
- include Git tags where useful;
- short SHA primary, full SHA available in detail;
- help/info controls explaining Workflow values;
- help/info controls explaining Git-operation states;
- better wrapping/layout for long branch names and identifiers.

## D. Dashboard — Working Tree

Current counts remain useful:

    Staged
    Unstaged
    Untracked
    Conflicts

Desired:

- Detail/View Files control;
- show which files belong to each category;
- preserve exact Git classification;
- this should later feed naturally into Stage review.

## E. Dashboard — Upstream

Current browser reports only locally known upstream state and performs no remote refresh.

Desired direction:

- current remote information should be obtainable through explicit fetch/refresh;
- show:
    upstream ref
    local relation
    ahead
    behind
    refresh state / freshness

Do not assume automatic background fetch is appropriate.

Determine the safest explicit refresh model.

Push remains later work.

## F. Snapshot Evidence

Current immutable snapshot IDs are technically correct but not human-friendly.

Desired human presentation includes concepts such as:

    Baseline before milestone
    Reviewed implementation
    Staged state
    Current pending state

Machine snapshot ID remains secondary evidence.

Investigate support required for:

- human-readable labels/purpose;
- branch/HEAD/state origin;
- Current vs Stale/Matching state;
- automatic or ensured snapshots at meaningful workflow boundaries;
- code-commit-to-code-commit lineage.

Do not assume existing snapshot schema contains enough information.

Determine what is already stored versus what would require new metadata.

    CODE COMMIT A

        ↓
    reviewed state
        ↓
    CODE COMMIT B

Documentation-only prompt/addendum/closeout commits must not obscure the actual code evolution.

Investigate how existing:

    Git HEAD
    snapshot
    comparison
    stage plan
    commit plan
    commit execution

can be linked into this model.

Determine what is already derivable and what would require an explicit higher-level record.

## H. Comparisons

- machine snapshot IDs secondary;
- clearer relationship to code commits/states;
- prevent or explicitly reject reversed Before/After selection when Repo Control can prove ordering;
- do not rely solely on Git ancestry because multiple snapshots can exist at the same HEAD.

Determine what ordering/lineage information currently exists.

## N. Whitespace / Formatting Control

Product Owner regularly encounters whitespace noise in prompts, addenda, and documentation.

Desired future capabilities:

Detection:

    trailing whitespace
    whitespace-only changes
    line-ending inconsistencies
    excessive/noisy blank-line changes where safely identifiable

Review:

    show all changes
    optionally hide whitespace-only differences visually

Cleanup:

    explicit user-approved normalization only

Never:

- silently ignore whitespace in the actual Git delta;
- silently rewrite files;
- stage a different result than the reviewed file state.

Investigate how existing `git diff --check` and Git diff mechanisms can support this safely.
